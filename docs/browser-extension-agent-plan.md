# WebLoom 浏览器 Agent 规划

## 1. 目标

构建一个尽量精简的浏览器插件 Agent，聚焦于基础问答能力。该 Agent 应全部运行在浏览器内，自动采集用户当前打开网页的上下文，并在模型判断有必要时自主调用 MCP 工具。

第一版重点优化以下目标：

- 架构简单
- 全流程浏览器内运行
- 网页上下文采集可控、可解释
- LLM 通过 OpenAI 兼容报文接入
- MCP 通过 HTTP 接入，并尽可能复用通用配置

## 2. 范围

### 第一版包含

- 浏览器插件内的聊天界面
- 基于当前网页上下文的基础问答
- 自动采集网页内容作为上下文
- 设置项支持“仅当前网页”与“所有打开网页”
- LLM 地址、模型、API Key 配置
- MCP 工具发现与调用
- 由模型自主决定是否调用工具

### 第一版不包含

- 额外运行独立后端服务
- 多端账号体系或云同步
- 复杂自动化工作流
- 跨设备同步的长期记忆系统
- 浏览器外的桌面集成

## 3. 产品形态建议

建议第一版只面向 Chrome，采用 Manifest V3 浏览器插件形态，主要由以下部分组成：

- `sidePanel`：主聊天界面
- `service worker`：Agent 编排核心
- `content script`：网页内容采集
- `IndexedDB` + `chrome.storage`：本地会话与配置存储

这样设计的原因：

- 能保证核心逻辑全部在浏览器内完成
- 不需要本地守护进程或独立服务
- 插件天然具备网页访问、UI 和网络请求能力，结构最直接

## 4. 核心使用流程

### 主流程

1. 用户打开插件侧边栏。
2. 插件根据当前设置自动采集网页上下文。
3. 用户输入问题。
4. Agent 将问题、历史消息、网页上下文、可用 MCP 工具一起组织给模型。
5. 模型直接回答，或先请求调用工具。
6. 如果模型请求调用工具，插件先展示确认信息，再决定是否执行。
7. 工具结果回传给模型，再生成最终回答。

### 交互形态

建议交互逻辑尽量接近 ChatGPT，但所有数据仍保存在本地：

- 支持多会话列表
- 支持新建会话
- 支持切换历史会话继续聊天
- 支持重命名、删除、清空会话
- 默认跨浏览器重启保留本地会话历史

这里要明确区分两个概念：

- 第一版**应保留本地会话上下文**
- 第一版**不做跨设备同步或独立知识库式长期记忆**

也就是说，产品应该像 ChatGPT 一样保留本地聊天记录和上下文连续性，但依旧遵循“无后端”要求。

### 核心设置项

- LLM Base URL
- API Key
- Model
- 上下文采集范围：`当前网页` / `当前窗口所有网页` / `所有打开网页`
- 上下文采集方式：静默自动采集
- MCP 服务配置
- API Key 存储方式：持久化 / 仅会话期
- 会话历史管理：本地持久化 / 手动清空
- 工具调用确认：展示来源 MCP、工具名、参数后再执行

## 5. 功能规划

### 5.1 基础问答

- 支持多轮对话
- 每次提问默认自动带上网页上下文
- 回答中尽量说明参考了哪些网页内容
- 支持基于历史会话继续追问，而不是每次从零开始

### 5.1.1 本地会话历史

建议将“本地会话历史”作为第一版核心能力：

- 每个会话在本地单独保存
- 会话包含标题、创建时间、最近更新时间、消息列表
- 用户关闭浏览器后，下次打开插件仍可继续之前会话
- 支持创建多个会话，交互方式尽量接近 ChatGPT

同时需要处理上下文窗口限制：

- UI 层保留完整本地历史
- 发送给模型时不一定带上全部历史，而是按策略裁剪
- 当历史过长时，可采用“最近若干轮 + 会话摘要”的方式组织上下文

这样既能保留完整聊天体验，也不会因为上下文无限增长导致成本和性能失控。

### 5.2 自动网页采集

插件支持三档采集范围：

- `当前网页`：只采集用户当前正在看的标签页
- `当前窗口所有网页`：采集当前浏览器窗口内所有可访问标签页
- `所有打开网页`：采集所有浏览器窗口中可访问的已打开标签页

采集方式确定为“静默自动采集”，即用户提问时默认自动整理上下文，不要求每次发送前手动确认。

建议第一版默认使用 `当前网页`，原因是：

- 隐私风险更低
- token 成本更低
- 相关性更稳定

建议每个网页提取以下信息：

- 标题
- URL
- 当前选中文本（如果有）
- 整页正文的主体可读文本
- 可选的标题层级 / 元信息

约束建议：

- 不采集 `chrome://` 等浏览器内部页面
- 每个页面设置最大采集长度
- 优先提取整页正文，而不是只取当前可见区域或原始整页 DOM

### 5.3 MCP 工具调用

- Agent 根据用户问题和工具描述，自主判断是否需要调用工具
- 工具以函数调用风格暴露给模型
- 实际工具调用由插件内的 MCP HTTP 客户端完成
- 任何工具真正执行前，都需要用户确认
- 确认界面至少展示：工具来源 MCP、工具名、调用参数

## 6. 技术架构

### 6.1 组成模块

#### A. 侧边栏 UI

职责：

- 聊天界面
- 会话列表与会话切换
- 设置界面
- 展示已采集上下文摘要
- 展示工具调用过程

#### B. 后台 `service worker`

职责：

- 编排提问与回答流程
- 收集标签页内容
- 维护对话状态
- 管理会话加载、保存与上下文裁剪
- 调用 LLM
- 运行 MCP 工具调用循环
- 做权限、超时和安全控制

这一层应作为 Agent 的主运行时。

#### C. `content script`

职责：

- 提取页面正文内容
- 返回结构化页面快照

建议快照结构：

```json
{
  "tabId": 123,
  "title": "示例页面",
  "url": "https://example.com",
  "capturedAt": "2026-04-19T14:00:00Z",
  "selection": "当前选中文本",
  "content": "裁剪后的页面正文"
}
```

#### D. 本地存储

建议区分两类本地存储：

- `IndexedDB`：保存会话历史、消息记录、较大的页面快照
- `chrome.storage.local`：保存插件设置、轻量配置、MCP 服务配置

建议本地保存以下内容：

- 对话历史
- 会话元数据
- 网页快照缓存
- 插件设置
- MCP 服务配置

原因：

- 类 ChatGPT 的多会话历史通常数据量较大
- 仅使用 `chrome.storage.local` 容易受容量和读写限制影响
- `IndexedDB` 更适合本地消息存档

## 7. LLM 接入方案

### 7.1 协议形式

LLM 接入建议采用 OpenAI 兼容报文格式，用户在插件设置中配置：

- Base URL
- API Key
- Model

这样可以在第一版减少对具体厂商的耦合，同时支持更多兼容服务。

### 7.2 请求组织方式

插件内部先使用统一的消息结构，再转换成 OpenAI 兼容请求体。请求中应包含：

- system prompt
- 当前会话中参与本轮推理的历史消息
- 当前网页上下文
- MCP 工具定义（启用时）

建议增加一层上下文组装策略：

- UI 保留完整本地会话历史
- Agent 运行时只抽取本轮真正需要的历史消息
- 长会话通过摘要压缩早期内容

这样既符合类似 ChatGPT 的体验，也适配模型上下文窗口限制。

### 7.3 API Key 安全性

这里需要明确一个现实约束：如果不引入后端，浏览器插件无法像服务端那样真正保护密钥。

建议方案：

- 默认允许用户手动配置自己的 API Key
- 提供“仅本次会话保存”模式，浏览器关闭后失效
- 如果用户选择持久保存，则保存到 `chrome.storage.local`
- UI 中展示时对 Key 做掩码处理
- 明确提示：浏览器插件场景下，API Key 只能做到“本地保存”，不能做到“服务端级别的密钥隔离”

结论：

- 对 BYOK（用户自带 Key）是可接受的
- 不适合在纯前端插件里保护平台自有密钥

## 8. MCP 通过 HTTP 接入

### 8.1 总体结论

建议采用“通用 MCP 客户端 + 每个服务单独实例配置”的方式。

也就是说：

- 客户端逻辑可以尽量通用
- 但每个 MCP 服务通常仍需要单独配置地址、鉴权头、启用状态

所以你提到的“是否存在通用配置”，答案是：

- **有，应该设计通用配置模型**
- **但具体到每个 MCP 服务，通常还是要分别填写自己的连接信息**

### 8.2 建议配置结构

```json
{
  "id": "docs-search",
  "name": "Docs Search",
  "baseUrl": "https://mcp.example.com",
  "transport": "http",
  "headers": {
    "Authorization": "Bearer ..."
  },
  "enabled": true
}
```

### 8.3 MCP 调用流程

1. 插件加载已启用的 MCP 服务配置。
2. 从 MCP 服务发现可用工具。
3. 将工具定义合并进模型可调用工具列表。
4. 模型决定是否调用工具。
5. 插件弹出确认界面，展示来源 MCP、工具名、参数。
6. 用户确认后，`service worker` 发起工具调用。
7. 工具结果回传模型，生成最终回答。

### 8.4 最小安全控制

即使第一版尽量简化，也建议至少加上：

- 每个服务单独启停
- 可选的工具白名单
- 调用超时控制
- UI 中明确显示本次是否发生了工具调用
- 工具执行前确认，并展示来源 MCP、工具名、参数

## 9. 网页捕捉策略

### 方案 A：当前网页

优点：

- 隐私更稳妥
- 上下文噪音更少
- 成本更低

缺点：

- 可能漏掉用户同时打开的参考资料页

### 方案 B：当前窗口所有网页

优点：

- 比单页更完整，适合同一任务下的多标签页浏览
- 相比“所有打开网页”，噪音和隐私风险更可控

缺点：

- 仍可能引入无关标签页
- token 消耗高于单页模式

### 方案 C：所有打开网页

优点：

- 适合研究型、多标签页对比任务
- 更符合“自动吸收上下文”的体验

缺点：

- 隐私风险更高
- token 消耗明显增加
- 上下文相关性更容易下降

第一版建议：

- 默认 `当前网页`
- 提供 `当前窗口所有网页` 与 `所有打开网页` 两个更大范围的显式开关
- 采用静默自动采集
- 在界面中持续展示本次实际纳入上下文的页面摘要

## 10. Agent 行为建议

建议将 Agent 的默认行为定义为：

- 优先使用当前采集到的网页上下文回答
- 只有在本地上下文不足时，才考虑调用 MCP 工具
- 简单问题尽量直接回答，不要过度调用工具
- 如果调用了工具，需要在结果中说明
- 避免重复调用同一个工具

这样更符合你提出的“尽量简化”的方向。

## 11. 关键约束与风险

### 浏览器插件约束

- `service worker` 生命周期是短暂的，需要注意状态恢复
- 某些页面可能不允许注入脚本或提取正文
- 浏览器内部页面不能采集
- 网络请求权限和站点权限需要提前声明

### LLM 接入约束

- 并非所有服务都完全兼容 OpenAI 报文
- 第一版需要流式返回，因此需要优先选择支持流式输出的兼容服务
- 某些 API 可能受浏览器 CORS 限制

### MCP 接入约束

- 不是所有 MCP 服务都提供适合浏览器环境的 HTTP 传输
- 依赖本地进程、stdio 的 MCP 服务不适合“纯浏览器插件”方案

因此第一版应明确限定：

- **仅支持可通过 HTTP 访问的 MCP 服务**

## 12. 实施阶段建议

### Phase 1：最小可用版本

- 侧边栏聊天 UI
- 本地多会话管理
- `当前网页` 采集
- OpenAI 兼容 LLM 配置
- 流式问答输出

### Phase 2：Agent 能力闭环

- MCP 服务配置 UI
- 工具发现
- 工具调用前确认
- 工具调用循环
- 回答中展示工具调用记录

### Phase 3：上下文增强

- `当前窗口所有网页` 与 `所有打开网页` 采集模式
- 页面快照预览
- 更好的上下文裁剪与排序

### Phase 4：安全与体验打磨

- 超时、重试、异常提示
- 更好的 Key 存储体验
- 更清晰的权限说明和隐私提示

## 13. 建议先拍板的决策

为了尽快收敛方案，建议先固定以下决策：

1. 插件形态采用 Chrome Manifest V3。
2. 第一版只做基础问答，不做复杂自动化。
3. 第一版默认支持本地多会话持久化，交互形态接近 ChatGPT。
4. 采集方式为静默自动采集。
5. 采集范围分为 `当前网页`、`当前窗口所有网页`、`所有打开网页` 三档。
6. 第一版只支持 HTTP 可访问的 MCP 服务。
7. MCP 采用通用配置模型，但每个服务单独配置实例。
8. 工具调用需要在执行前确认，并展示来源 MCP、工具名、参数。
9. API Key 采用 BYOK 模式，并明确安全边界。
10. 第一版需要流式输出。
11. 页面采集以整页正文为主。
12. 不引入额外后端，所有编排都放在插件内完成。

## 14. 已确认决策

以下内容已经确认，可作为后续设计与实现的固定前提：

1. 第一版目标浏览器只考虑 Chrome。
2. 网页上下文采用静默自动采集。
3. 采集范围拆分为三档：`当前网页`、`当前窗口所有网页`、`所有打开网页`。
4. MCP 工具调用需要执行前确认，确认界面展示来源 MCP、工具名、参数。
5. 本地会话支持重命名和删除，不需要置顶。
6. 第一版需要流式输出。
7. 页面采集优先取整页正文。
